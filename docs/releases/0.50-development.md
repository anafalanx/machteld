# Machteld 0.50-dev measurements

These measurements use unsigned Windows x64 builds on an Intel Core i7-1255U.
The language edition is 1 and the host package API is 30. The timings are
medians on the development machine with a warm filesystem. The most recent
run began after all project builds and qualification suites had finished.

## Compiling X source

At `f2413f7`, the 0.50-dev compiler checked the two small command-line
sample projects in 84 ms and 118 ms from a fresh process. Packing them
took 1.13 s and 1.08 s respectively. Running a packed archive executes the
generated Tcl directly.

| Input | Modules | Physical lines | Check, compiler loaded | Check and emit Tcl |
| --- | ---: | ---: | ---: | ---: |
| Typed pages | 2 | 58 | 9.5 ms | 10.5 ms |
| Typed timeline | 1 | 97 | 18.9 ms | 19.1 ms |
| Typed colleague import | 1 | 106 | 15.8 ms | 15.8 ms |
| 10 copies of the import module | 10 | 1,060 | 153 ms | 162 ms |
| 100 copies of the import module | 100 | 10,600 | 1.52 s | 1.75 s |

The large full compile ranged from 1.61 to 1.92 s across five measured
runs. The larger projects repeat a real import module under distinct
module names. Physical line counts include comments and blank lines.
Loading and measuring the same three examples in memory excludes process
startup, file input and archive creation. Each action discarded one
warm-up. The command-line medians use nine subsequent process launches.

## Calling a migrated Tcl package

At `43755b2`, both variants ran the same entry and field-name package from
`examples/mixed-migration`. The Tcl-only variant used the original caption
package and a manifest with zero X modules. The mixed variant called an X
export and passed back into Tcl to look up the field name. Both used the
same Tcl procedure to dispatch and check each callback.

| Measurement | Tcl-only project | Mixed project |
| --- | ---: | ---: |
| Check in a fresh process | 120 ms | 145 ms |
| Pack in a fresh process | 1.44 s | 1.80 s |
| Start from source and render one caption | 126 ms | 135 ms |
| Start from an archive and render one caption | 82.5 ms | 83.1 ms |
| One callback in a batch of 40,000 | 2.78 µs | 8.34 µs |
| Observed peak process working set for the batch | 17.29 MiB | 18.10 MiB |
| Archive containing source and benchmark entry | 89,672 bytes | 102,513 bytes |

The callback ran 10,000 cycles over four inputs, including leading zeros,
Unicode and empty text. Each call checked the exact returned caption.
The in-process timer covered dispatch and verification. The startup rows
included launching the process and servicing one callback through the Tcl
event loop. The controller sampled the Windows peak working set about every
three milliseconds. Seven measured rounds followed a warm-up and alternated
the order of the variants.

The extra checked crossings cost about 5.6 µs per caption in this small leaf.
A conversion that keeps more work on one side of the boundary needs its own
comparison. Both variants used the same 15,223,467-byte executable with SHA-256
`e4ac637ad32ef19e06ede9b61e0c71456293cdc30700b979f67190a6730341bd`.

## Reproducing and moving the combined runtime

Two fresh checkouts of `6942ee2` built the same 15,264,910-byte Windows x64
executable. Each build used its own freshly bootstrapped dependency cache,
the eleven pinned local inputs and `SOURCE_DATE_EPOCH=1795698771`. The
executable's SHA-256 was
`1c3ae388aea815e925c8f254abdf681fec3a2f95b0a4bdd289ab79b99ea8fa98`.
All twenty compiler files matched their source bytes. The embedded manual
held 499 documents and had SHA-256
`607459e1163bff9ccc522cb2acf0792ea1b90ff605ca432a32077cd8698df446`.

All 38 packaging steps passed on the resulting runtime. Between the
packaging gate and the separate direct runs, all 39 compiler test suites
ran on these bytes. Two further generations of the reference reproduced
the embedded database byte for byte.

Of 991 files in the two dependency manifests, 988 matched. Three build tools
differed. The static Tcl and Tk launchers contained different ZIP timestamps,
while every embedded library file matched. The SQLite DLL used to generate
the manual had a different preferred image base in each cache.

A mixed Tcl/X project passed its examples, ran from source and packed with
only the Windows system directory on the command path. After moving the
sources aside, the recipient directory contained just `machteld.exe` and
the archive. The copied application returned the expected Unicode caption.
Its recipient recovered the original files and bundled compiler, changed
the formatter, reran the examples and packed a second archive. Both archives
then produced their own expected captions from an unrelated directory.

## Finding the language manual offline

At `6513458`, the reference also indexes the full compiler guide shipped
with editable applications. `machteld.exe --docs get "project check"`
opens the relevant section. `machteld.exe --docs get require_index` opens
the list operations and their error contract. The manual has 36 sections
under `machteld/guide/application-compiler`.

Independent clean builds produced a 15,343,366-byte executable with SHA-256
`c005afe7874dd8a3b808b9042b02300afda5dc0b80688fd3f28962f4cc50d1fc`.
The extra manual and lookup entries added 78,456 bytes (76.6 KiB) to the
executable relative to `6942ee2`. The resulting 500-document SQLite
reference occupies 9,859,072 bytes before compression and has SHA-256
`242745ed0749f7d8e655ad52ea13b2031048ee231672d2753dc98461a9b13dd3`.
A clean checkout of the subsequent development-cache correction at
`f2413f7` reproduced the same executable byte for byte. Its cache regression
passed all 360 checks, including a change to the compiler README that
preserved the file's modification time.

## Moving data from signed 0.21

Both runtimes ran the original 0.21 console fixture with three arguments,
including a leading-zero identifier and Unicode. The development runtime
read the original binary store value from a copied 0.21 database. The
signed runtime then reopened that copy and recovered the new UTF-8 value
written by the development runtime.

Both versions accepted all 95 required valid JSON inputs and rejected all
188 required invalid inputs in the 0.21 corpus. Of the 35 inputs for which
the JSON suite allows an implementation choice, ten malformed UTF-8 byte
strings changed from acceptance in 0.21 to rejection in 0.50-dev. Pass
valid UTF-8 bytes to the JSON reader, or explicitly decode text in its
source encoding before passing it to the reader.
